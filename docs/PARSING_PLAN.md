# План: качественное преобразование pptx и docx в md

Документ — план работ, а не описание готового. Конвертация в md — первый шаг
конвейера, и её ошибки дальше не исправляются: поиск, генерация и проверки
работают только с тем, что попало в md. Поэтому здесь качество важнее
скорости, а прогон корпуса может идти ночью.

**Статус:** П1 сделан (см. таблицу этапов). Находки П1, важные для П2:

- отчёты сделаны в **think-cell**: у диаграмм в XML нет имён рядов и категорий —
подписи лежат отдельными надписями-полями (`a:fld`), сопоставление с данными —
только по расположению (П2);
- тепловые карты — таблицы, где значение задано **цветом заливки**: парсер
сохраняет цвет (`■ #54CFD6`), П2 сопоставляет его с легендой слайда;
- раздел определяется по слайду-разделителю («01» + заголовок), подраздел — по
колонтитулу над заголовком, повторяющемуся не меньше чем на 3 слайдах;
- разбор изображений нужен на 50 слайдах из 147.

## 2. Входные форматы

- **pptx** — основной: отчёты и КП в виде презентаций.
- **docx** — отчёты и КП в Word. Особый случай: **в документ вставлены
скриншоты слайдов**. Для системы такой скриншот — полноценный слайд: его текст,
таблицы и числа должны попасть в md и быть доступными поиску, иначе
значимая часть содержания пропадёт молча. Чисел из XML для скриншота нет,
поэтому всё, что с него распознано, помечается как OCR.
- Позже, по SPEC: pdf (текстовые и сканы).



## 3. Целевой формат md (контракт)

Сохраняется текущий формат презентаций (frontmatter, `<!-- slide: N -->`,
`## [Слайд N] …`, поля раздела, блоки через `---`). Добавляется:

- во frontmatter: `converter_version`, `source_format: pptx|docx`, модель VLM;
- у каждого слайда или рисунка — **происхождение данных**:
`**Источник значений:** xml | ocr | интерпретация`;
- для docx:
  - `<!-- page: N -->` — номер страницы из рендеринга (для ссылок «стр. N»);
  - заголовки документа — `#`/`##`/`###` по уровням Word;
  - скриншот слайда — блок
  `<!-- figure: N; kind: slide_screenshot; page: P -->` с транскрипцией как у
  слайда (заголовок, текст, таблицы) и подписью рисунка из документа;
  - прочие рисунки (схема, фото, логотип) — короткое описание или пропуск по типу.

Чанкер под docx: разделы по заголовкам с целевым размером из SPEC, а блок
скриншота слайда — неделимый чанк, как слайд в pptx.

## 4. Архитектура конвертера

Три слоя. Принцип: **всё, что можно взять из файла точно, берётся кодом;
модель только видит картинку и объясняет визуал**.

### 4.1 Детерминированное извлечение (истина)

**pptx** (python-pptx + прямой разбор XML):

- порядок и скрытые слайды, заголовки, текстовые блоки с уровнями списков;
- рекурсивный обход групп фигур, порядок чтения по координатам;
- таблицы с объединёнными ячейками;
- диаграммы: серии, категории, значения из `ppt/charts/chartN.xml`, точно;
- гиперссылки, alt-текст картинок, непустые заметки;
- перечень картинок со слайда (что потом нужно показать VLM).

**docx** (python-docx; Docling — как вариант для сложной вёрстки):

- иерархия заголовков, абзацы, списки, таблицы, сноски, подписи рисунков;
- вставленные картинки с позицией в тексте и подписью; EMF/WMF — растрировать.

Результат слоя — JSON-структура документа: она же основа для проверки.

### 4.2 Рендеринг

Каждый слайд и каждая страница — в PNG (150–200 dpi). На ноутбуке
установлены PowerPoint и Word: экспорт в PDF через AppleScript, затем
`pdftoppm`. Альтернатива без Office — LibreOffice в фоновом режиме (нужно поставить).
PDF заодно даёт номера страниц docx.

### 4.3 Проход мультимодальной модели (VLM)

На каждый слайд (и на каждый скриншот слайда в docx):

- вход: PNG + извлечённая структура слайда (JSON);
- задача: собрать md по контракту — порядок чтения, структура, «Тип слайда»,
«Ключевой посыл», «Визуал», расшифровка схем («A → B»), значения тепловых
карт и шкал;
- жёсткие правила: числа и тексты из JSON переносятся как есть; новое число
допустимо только с картинки и помечается `ocr`; ничего не дописывать от себя.

Для docx сначала **классификация картинок** (скриншот слайда / диаграмма /
схема / фото / логотип), затем для скриншотов — полный проход как для слайда:
специализированная OCR-модель даёт текст, VLM — структуру и визуал.

## 5. Выбор моделей

Конвертация — пакетная и ночная, поэтому модель может быть тяжелее, чем для
ответов. На 16 ГБ одновременно в памяти одна модель, конвертация не идёт
параллельно с Qwen 9B.


| Вариант                                | Где                       | Роль                                           | Оценка                                                  |
| -------------------------------------- | ------------------------- | ---------------------------------------------- | ------------------------------------------------------- |
| **Qwen3-VL 8B** (`qwen3-vl:8b`, ~6 ГБ) | ноутбук, Ollama           | основной VLM: структура, визуал, интерпретация | сильный OCR и документы среди локальных; кандидат №1    |
| **GLM-OCR / PaddleOCR-VL** (~1B)       | ноутбук                   | текст со скриншотов слайдов в docx             | быстрые специализированные OCR, точнее на мелком тексте |
| **Gemma 4 12B** (`gemma4:12b`)         | ноутбук                   | альтернатива Qwen3-VL для A/B                  | на 16 ГБ впритык                                        |
| **Qwen3-VL 4B**                        | ноутбук                   | быстрая классификация картинок docx            | дешёвый первый проход                                   |
| Qwen3-VL ~30B / 32B                    | сервер с GPU 24 ГБ (SPEC) | промышленный прогон, если 8B не дотянет        | требует сервера                                         |
|                                        |                           |                                                |                                                         |


Выбор — по замеру (раздел 7), а не по бенчмаркам. Скорость на слайд на M5
неизвестна: замерить в П2 и пересчитать время ночного прогона корпуса.

## 6. Автоматическая проверка (блокирующая)

Документ не идёт в реестр и индекс, пока не пройдёт:

- **сверка чисел** md ↔ XML (прототип уже есть): число из md без опоры в XML
допустимо только с пометкой `ocr`/«интерпретация»; диаграммы — точное совпадение;
- **полнота текста**: ≥ 95% текстовых фрагментов XML присутствуют в md
(с нормализацией пробелов и переносов);
- **структура**: число и порядок слайдов, метки, таблицы с одинаковым числом
ячеек в строках, заполненные обязательные поля;
- **docx**: все заголовки на месте, каждый скриншот слайда транскрибирован,
у каждого рисунка есть номер страницы;
- **уверенность по слайду**: слайды с OCR, тепловыми картами и низкой
полнотой — в очередь ручной проверки.



## 7. Оценка качества и выбор модели

- **Эталон**: md ДЕВ (Claude, сверен с XML) + 2–3 docx, проверенных вручную.
**Нужно от пользователя**: 2–3 типичных docx, в том числе со скриншотами слайдов.
- **Метрики**: точность и полнота чисел; полнота текста; точность заголовков;
точность ячеек таблиц (выборка); ручная оценка «Посыла» и «Визуала» на 30
случайных слайдах (критерий SPEC «30 страниц на соответствие оригиналу»).
- Каждая модель из раздела 5 прогоняется на одном и том же эталоне; итог — таблица
«качество × время на слайд».



## 8. Ручная проверка в интерфейсе

Вкладка «Конвертация» в Streamlit: слева картинка слайда или страницы,
справа md, сверху найденные проверкой проблемы; кнопки «принять» и
«исправить». Принятый документ сразу уходит в черновик реестра
(`python -m bzpo.registry draft`) — цепочка «файл → md → реестр → индекс»
замыкается в одном месте.

## 10. Риски и открытые вопросы

- **Конфиденциальность**: можно ли отправлять слайды во внешний API (Claude)
хотя бы для эталона и судейства на обезличенной выборке?
- **Скорость** локального VLM на 147 слайдах неизвестна — возможен перенос
прогона на сервер.
- **Скриншоты низкого разрешения** в docx: OCR мелкого текста может не
дотянуть — такие рисунки помечать и отправлять на ручную проверку.
- **EMF/WMF** — растрирование без Office и LibreOffice ненадёжно.
- **Рендер через PowerPoint и Word** требует установленного Office; для
сервера нужен LibreOffice.
