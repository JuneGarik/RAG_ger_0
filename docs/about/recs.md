# Замечания по итогам ревью SPEC v1.0

15 августа 2026. Два независимых ревью: инженерное (разработчик RAG) и критическое. Все замечания ниже учтены в SPEC.md v1.1; документ нужен, чтобы отразить их в Word-концепции «2_RAG_konveyer» (следующая версия после 2.5). Пометка у каждого пункта: **[SPEC]** — исправлено в SPEC 1.1, **[концепция]** — требует правки текста концепции, **[орг]** — организационное решение вне документов.

---

## Часть 1. Замечания критика

### Блокирующие

1. **Схема данных не исполнялась.** `documents` ссылалась на `projects`, `chunks.parent_section_id` на `sections` — таблицы создавались ниже по скрипту. Порядок зафиксирован: справочники → проекты → документы → разделы → чанки → артефакты → рёбра. [SPEC]

2. **Обогащение контекстом уничтожало дедупликацию.** Эмбеддинг строился по `text_enriched`, дедупликация — по косинусу 0.95. Обогащение приписывает каждой копии типового блока разного заказчика и год, близость копий падает ниже порога, и сценарий «десять одинаковых абзацев про PMBOK», ради которого дедупликация вводилась, перестаёт детектироваться. Введён второй вектор `embedding_raw` по `text_raw` — только для дедупликации, MMR и семантических рёбер. [SPEC] [концепция — в раздел 6.4 добавить, по какому представлению считается близость]

3. **Результат дедупликации нигде не читался.** `cluster_id` и `is_canonical` заполнялись и не использовались ни в поиске, ни в генерации. Теперь: фильтр `is_canonical = true` во всех поисковых запросах, разворачивание кластера в списке «Источники» («встречается также в: …»), метрика уникальности считается по кластерам. [SPEC]

4. **Дедупликация стояла до векторизации.** Считать косинусную близость до получения векторов невозможно; `embedding NOT NULL` к тому же не позволял записать чанк до векторизации. Шаги переставлены: векторизация 7-м, дедупликация 8-м. [SPEC]

5. **Секционный индекс строился, но не использовался.** Главное решение концепции v2.5 — генерация по образцу с подачей 2–3 полных разделов — в онлайн-конвейере отсутствовало: поиск шёл только по `chunks`. По старому SPEC получилась бы вопросно-ответная система, от которой концепция отказалась явно. Добавлена обязательная секционная ветвь: поиск по `sections` → реранкинг → 2 раздела-образца как основной материал контекста. [SPEC] [концепция — убедиться, что в разделе 10.2 механизм отбора образцов описан, а не только назван]

6. **Эталонный датасет нельзя было привязывать к chunk_id.** Идентификаторы чанков пересоздаются при каждой смене параметров чанкинга — разметка обнулялась бы, а сравнение вариантов чанкинга и есть главное назначение датасета. Переведён на устойчивые якоря: (документ, диапазон страниц/раздел, цитата 1–2 предложения) + резолвер в чанки текущей версии индекса. [SPEC] [концепция — раздел 12.1, состав записи датасета]

7. **Якорная разметка датасета не имела ни оценки трудоёмкости, ни владельца.** Оценка «2–3 часа» в концепции относится к сбору формулировок; разметка того, какие фрагменты 12 500 страниц обязаны быть найдены, — 3–5 рабочих дней человека, знающего корпус. Назначение исполнителя со сроком — блокирующий пункт этапа 0. [SPEC] [орг]

8. **Базовая линия этапа 3 и результат 3.5 были несравнимы.** База — 8 чанков, слой разбора — до 48 чанков и 300 кандидатов: прирост Recall гарантировался арифметикой размера выдачи, критерий «нет прироста → слой отключается» не мог сработать. Введена метрика Recall@K_ctx на итоговом контексте при равном бюджете токенов. [SPEC] [концепция — раздел 12.2]

9. **Цель Recall@8 ≥ 0.85 могла быть недостижима арифметически.** При 15 эталонных чанках на широкий запрос максимум Recall@8 = 0.53. Число якорей на запрос не ограничено, поэтому цель интерпретируется по медиане, широкие запросы отслеживаются отдельно. [SPEC]

10. **Фильтр публичности висел на поле без FK и без процедуры заполнения.** `chunks.project_id` был nullable без внешнего ключа; поведение при NULL не определено (INNER JOIN молча теряет чанк, LEFT JOIN молча пропускает мимо фильтра). В офлайн-конвейере не было шага сопоставления файла с проектом реестра. Теперь: `project_id NOT NULL REFERENCES projects`, явный шаг 0 «сопоставление файл→проект», файл без проекта в индекс не попадает («по умолчанию закрыт»), готовый предикат фильтра в SPEC. [SPEC] [концепция — раздел 10.5, первый рубеж]

11. **Стоимость и вход шага обогащения не были определены.** 20 тыс. вызовов локальной модели — самая дорогая операция проекта, а промпт, вход, поведение при сбое и кэширование не описаны. Зафиксировано: вход — чанк + метаданные из реестра (не документ целиком), промпт версионируется, детерминированный фолбэк из метаданных, кэш по (хэш текста, версия промпта). [SPEC] [концепция — раздел 6.2 дополнить контрактом]

12. **Тезис «переиндексация за полторы минуты» был неверен без кэша обогащения.** Полторы минуты — только векторизация; смена чанкинга без кэша тянет повторную ночь GPU на обогащение. Кэш обязателен, время первичной индексации и переиндексации разведено. [SPEC] [концепция — разделы 5 и 11.1, где фигурируют «1,5 минуты»]

13. **Проба GigaChat-20B-A3B отсутствовала в блокирующем списке.** Существование q4_K_M-сборки, поддержка MoE в llama.cpp, шаблон чата и скорость 80–130 ток/с — непроверенные допущения, на которых стоит весь расчёт латентности. Проба добавлена в блокирующий список (полдня), запасной вариант Qwen3.5-27B назван явно. [SPEC] [орг]

14. **Закупка GPU не имела владельца, срока и места в плане.** Добавлена в блокирующий список этапа 0 с требованием зафиксировать владельца и срок. [орг] [концепция — раздел 15, этап 0]

15. **Лексический поиск в наивной реализации возвращал бы пустоту.** `plainto_tsquery` от гипотезы HyDE на 150 слов даёт конъюнкцию всех лемм — ноль совпадений, половина схемы поиска молча вырождается. Зафиксировано: дизъюнкция 8 наиболее редких лемм по IDF, `ts_rank_cd`; добавлен параметр глубины списков `PER_LIST_K`. [SPEC]

16. **Загрузчик БД подтверждений отсутствовал как компонент.** Excel-валидация из концепции (5 проверок, версионирование загрузок) в SPEC не попала. Добавлен модуль с таблицей `registry_uploads`. [SPEC]

17. **Метаданные, ради которых блокировался старт, не имели потребителя.** `tender_result` и прочие поля объявлялись boost-ом, но формулы, весов и места применения не было. Задана формула boost (после реранкинга, до MMR), веса в конфигурации. [SPEC] [концепция — раздел 9.4]

18. **Критерии завершения этапов были в большинстве непроверяемы.** «20 тыс. чанков в базе» — счётчик, «связные разделы со ссылками» — вкусовая оценка. Все критерии переписаны на объективные (идемпотентность двойного прогона, ≥98% чанков в границах, ≥90% якорей разрешаются, автотесты зелёные, согласованность оценок ≥0.7 и т. д.). [SPEC] [концепция — раздел 15]

19. **Требований к интерфейсу не было, а два этапа на них опирались.** Пометка «не по делу», загрузка итогового документа, связь ответа с загруженным документом — всё требовалось трассировкой, но не планировалось как работа. UI внесён в план (задача 4.7); событие copy штатно в Streamlit не снимается — перенесено в MVP+. [SPEC] [концепция — раздел 13.4, оговорка про copy]

### Некритичные

20. Инкрементальное обновление не поддерживалось схемой: не было хэшей содержимого на разделах и чанках. Добавлены `content_hash`. [SPEC]
21. Версионирование и откат индекса не были реализуемы: `index_version` нигде не читался. Добавлена таблица `index_versions`, фильтр активной версии во всех запросах, атомарное переключение после регрессии. [SPEC]
22. Поля заполнялись и не использовались (`is_table`, `ocr_low_conf`, `token_count`, `ord`). Для `ocr_low_conf` определён потребитель: пометка «⚠ OCR» в списке источников. [SPEC]
23. Кластеризация «объединение пар» — одиночная связь, цепочки могут слить несхожие тексты. Метод назван (связные компоненты), возвращены ручной просмотр 20 кластеров и запасной порог 0.97. [SPEC]
24. Порог реранкера калибровался на неизвестном числе примеров. Зафиксирован минимум: ≥15 запросов без ответа. Поведение при частично ненайденных гранях определено (блок «Не найдено в корпусе», отказ при всех/обязательных гранях). [SPEC]
25. «Единицы миллисекунд» на поиск оптимистичны: 24 последовательных скана таблицы с текстами на запрос. Внесено требование замера p50/p95 на этапе 3. [SPEC]
26. Расчёт латентности выпал из SPEC целиком. Возвращён с разбивкой по стадиям, учётом сериализации Ollama и компенсаторами. [SPEC] [концепция — раздел 11.4 пересчитать: шесть гипотез HyDE последовательно — это 7–11 с, а не часть «4–8 с» на весь разбор]
27. Кэш векторов запросов без ключа версии модели после обновления модели отдавал бы несовместимые векторы. Ключ дополнен (модель, ревизия); гипотезы HyDE не кэшируются. [SPEC]
28. Перевод anon→closed в данных необратимо терял разметку. Заменён конфигурацией `ALLOWED_PUBLICITY=['open']` без мутации данных. [SPEC] [концепция — раздел 10.5 и «Открытые вопросы»]
29. Не посчитано, сколько корпуса останется после фильтра публичности. Добавлен стоп-гейт: <60% корпуса в open → пересмотр жизнеспособности PoC до старта. [SPEC] [орг]
30. `page_start/page_end NOT NULL` при DOCX/PPTX без понятия страницы. Поля стали nullable, роль LibreOffice (рендеринг в PDF для нумерации) описана. [SPEC]
31. У `documents` не было названия — в «Источники» пошли бы пути к файлам. Добавлены `documents.title` и `artifacts.title`. [SPEC]
32. `artifacts` и `documents` описывали одни файлы без связи. Добавлен `artifacts.doc_id`; `doc_type` очищен от смешения с форматом файла (`pptx` → `presentation`). [SPEC]
33. Три плана против семи шаблонов разделов не образовывали пар. Введена таблица соответствия типов задач, планов и разделов + тест рассинхронизации. [SPEC] [концепция — раздел 8.4]
34. Шаг 1 конвейера читался двусмысленно: «классификация типа файла постранично». Уточнено: классифицируется тип страницы (текст/скан), тип документа берётся из реестра. [SPEC]
35. Человеческая оценка не операционализирована: не было чек-листа, пересечения оценщиков, меры согласованности. Добавлено: фиксированный чек-лист, пересечение 30 ответов, согласованность ≥0.7. [SPEC] [концепция — раздел 12.3]
36. Метрика «доля уникальных блоков» не определяла, что такое блок. Определено: различные `cluster_id`. [SPEC]
37. Офлайн-конвейер оставался без наблюдаемости: качество обогащения никак не измерялось. Добавлены структурированный лог с этапа 2 и обязательная выборочная проверка обогащения (50 чанков по чек-листу) до полного прогона. [SPEC]
38. Не было чекпоинтов индексации: судьба наполовину проиндексированного корпуса не определена. Добавлены статусная модель документов, транзакция на документ, перезапуск failed. [SPEC]
39. Поведение при превышении лимита эмбеддера для секций не выбрано. Правило: разбиение записи секционного индекса на части ≤ SECTION_MAX_TOKENS. [SPEC]
40. Нет удаления, временных меток, бэкапа, аутентификации; трассы содержат тексты закрытых документов. Идентификация пользователя на PoC — выбор имени при входе; бэкап и жизненный цикл — зафиксировать в концепции (глава 14). [SPEC частично] [концепция]

### Расхождения SPEC ↔ концепция v2.5 (для сверки при правке Word)

- Приоритет подтверждений в сценарии А (ключевое изменение v2.5) не был перенесён в сборку контекста — теперь в SPEC 5.3. Проверить формулировку в концепции.
- Этап 0.5 (модуль изоляции до начала разработки) выпадал из порядка работ — возвращён.
- Сроки и исполнители этапов в SPEC отсутствовали — в концепции есть; при правке синхронизировать с реалистичным календарём из PLAN.md (5–6 месяцев против ~4).
- Из блокирующих вопросов Приложения А терялись: батч пар реранкера за вызов, схема лимита 20 rps (по запросам или элементам), ревизии моделей. Возвращены в SPEC 15.
- Вопрос про health-эндпоинт в концепции открыт, а SPEC утверждал «эндпоинта нет» без источника — теперь помечено «уточняется probe_api».
- Организационные пункты (владелец БД подтверждений после PoC, ежеквартальная сверка, ответственный за добавление документов) возвращены в SPEC 15.
- Раздел рисков концепции (15 рисков) в SPEC не переносился — риски исполнения плана теперь в PLAN.md, технические остаются в концепции.
- Правило «низкая уверенность классификации → расширенный план со всеми гранями» терялось — возвращено в SPEC 5.1.
- Запрет самореферентного судьи: SPEC писал «автоматическая оценка после калибровки» без указания модели, что на on-premise сводилось к той же GigaChat. Уточнено: внешняя модель офлайн на обезличенной подвыборке.

## Часть 2. Замечания разработчика

Пункты, совпадающие с частью 1, не повторяются — ниже то, что добавил инженерный взгляд.

### Схема и данные

41. CHECK-ограничения на все перечислимые поля (`publicity`, `doc_type`, `tender_result`, `company_role`, `status`, `artifact_type`, `edge_type`): опечатка `Closed` проходила фильтр `<> 'closed'` и означала утечку закрытого заказчика. [SPEC]
42. Реестр версий индекса `index_versions` с составом: модель и ревизия эмбеддера, версия парсера, параметры чанкинга, версия промпта обогащения, статус. [SPEC]
43. `documents.doc_date` — дата документа для boost по свежести (было только `parsed_at`). [SPEC]
44. Индексы `chunks(cluster_id, is_canonical)`, `documents(file_hash)`, `UNIQUE(file_path)`. [SPEC]

### Конвейер индексации

45. Токенизатор зафиксирован: все размеры — токенизатором bge-m3, бюджет генерации проверяется токенизатором GigaChat ×1.2 (расхождение токенизаторов до полутора раз). [SPEC]
46. Правило нарезки крупных таблиц: по строкам с повторением шапки и подписи. [SPEC]
47. Перекрытие 15% — только внутри раздела, с конца предыдущего чанка (иначе конфликт с иерархическим чанкингом и завышение близости соседей). [SPEC]
48. Дедупликация — блочным матричным умножением, не полной матрицей 20000×20000 (~1.6 ГБ float32). [SPEC]
49. Контракт со слоем подготовки данных (часть 1): JSON-схема входа с иерархией разделов, типами блоков, страницами, уверенностью OCR. Самый крупный пробел — модуль индексации нельзя было начать писать. [SPEC] [концепция — сослаться на схему в части 1]

### Онлайн-конвейер

50. Weighted-RRF вместо простого RRF: утверждение «гипотеза может только добавить кандидатов» для RRF без весов неверно — кандидат исходного запроса вытесняется из среза 50. Веса запрос 1.0 / гипотеза 0.7. [SPEC] [концепция — раздел 8.3, формулировка гарантии]
51. Вход реранкера определён: `text_raw`, усечение до лимита сервиса с конца (TEI по умолчанию режет по 512 токенов — чанк на 600 терял хвост молча). [SPEC]
52. MMR: min-max-нормировка обоих слагаемых (шкала реранкера 0–1 и косинус 0.6–0.9 несопоставимы; без нормировки MMR вырождается в порядок реранкера). Близость между чанками — по `embedding_raw`. [SPEC]
53. Сборка контекста специфицирована: порядок (образцы → факты → чанки), дедуп между гранями по chunk_id и cluster_id, бюджет 12000 токенов, усечение только хвоста чанков. [SPEC]
54. Контракты всех LLM-вызовов: JSON-схемы, temperature 0 (HyDE 0.7), 2 ретрая, детерминированные фолбэки. Оговорка об «уверенности»: Ollama не отдаёт логпробы, самооценка квантизованной модели плохо откалибрована — порог калибруется по матрице ошибок. [SPEC]
55. Реестр параметризованных запросов как файл в git: id, SQL, JSON Schema параметров, типы задач; фильтр публичности включён в каждый шаблон. [SPEC]
56. Правила маркеров [N]: нумерация по порядку в промпте, битый маркер удаляется на постобработке, гранулярность проверки — предложение. [SPEC]
57. Рантайм-ассерт инварианта HyDE в дополнение к тесту (сборка промпта будет меняться, один тест не защищает). [SPEC]

### Внешний сервис

58. Контракт интеграции: таймауты connect/read, Retry-After при 429, сортировка ответа по полю `index` (порядок не гарантирован), лимит параллелизма. [SPEC]
59. Нормализация векторов (L2=1) и оператор `<=>` зафиксированы — иначе пороги 0.95 и 0.75–0.85 не определены. [SPEC]
60. Деградация при отказе посреди запроса: отказ целиком, частичный ответ не выдаётся (для тендерного текста немаркированная неполнота опаснее отказа). [SPEC]
