# Профиль ноутбука: MacBook M5, 16 ГБ

Вся система на одной машине, без внешнего сервиса и без GPU-сервера.
Включён в `config.yaml` по умолчанию (`external.provider: local`).

## Состав

| Роль | Модель | Где работает | Память |
|---|---|---|---|
| Эмбеддинги | `ai-sage/Giga-Embeddings-instruct-480M-0826`, 1024 изм., вход до 8192 ток. | в процессе, sentence-transformers на MPS | ~1 ГБ |
| Реранкинг | `BAAI/bge-reranker-v2-m3` | в процессе, CrossEncoder на MPS | ~1.2 ГБ |
| LLM на запрос (`query`) | `qwen3.5:9b`, Q4_K_M | Ollama | ~6.6 ГБ + KV-кэш |
| LLM индексации (`enrichment`) | `GigaChat3.1-10B-A1.8B` (Lightning), GGUF Q4_K_M | Ollama | ~6.5 ГБ + KV-кэш |
| Хранилище | PostgreSQL 18 + pgvector | Postgres.app | ~0.5 ГБ |

В памяти одновременно одна LLM: Ollama выгружает одну и загружает другую
(~4 с), а индексация и ответы на запросы по времени не пересекаются.

Итого ~9–10 ГБ под систему; остальное — macOS и приложения. Браузер с
десятком вкладок съедает разницу, при индексации его лучше закрыть.

## Почему эти модели

**Эмбеддер — Giga-Embeddings 480M, не 3B и не 10B.** Линейка `0826` вышла
в августе 2026 (MIT), три размера:

| Модель | ruMTEB | Размерность | Веса bf16 | На 16 ГБ |
|---|---|---|---|---|
| 480M-0826 | 70.98 | 1024 | ~1 ГБ | да |
| 3B-0826 | 74.57 | 2048 | ~6 ГБ | только без LLM в памяти |
| 10B-A1.8B-0826 (MoE) | 74.99 | 1536 | ~21 ГБ | нет |

Дополнительно у 480M размерность 1024 совпадает со схемой `vector(1024)` — миграция не
нужна. У 3B 2048 измерений: это больше предела HNSW-индекса pgvector для
типа `vector` (2000), понадобился бы `halfvec` и новая миграция. Переход на
3B имеет смысл на сервере, и только если метрики этапа 3 упрутся в эмбеддер.

Модель асимметрична. Перед запросом ставится инструкция
`Instruct: …\nQuery: `, а тексты корпуса кодируются без неё. Поэтому векторы
запросов идут только через `embed_queries`, тексты корпуса и гипотезы HyDE —
через `embed`. Метод `embed_queries` у внешнего сервиса работает так же,
так что вызывающий код от провайдера не зависит.

**LLM — две модели по ролям** (`ollama.model_query`, `ollama.model_enrichment`).
Клиент Ollama создаётся с ролью, вызывающий код имён моделей не знает.

Роли выбраны по сравнению на трёх задачах БЗПО (temperature 0, без рассуждений):

| Задача | GigaChat 3.1 Lightning | Qwen3.5 9B |
|---|---|---|
| Раздел заявки с маркерами [N] | выдумал абзац фактов («методология водопада», «95%», «в рамках бюджета»), сослался на несуществующий [4] | все факты из контекста, маркеры верные; 2 рекламные фразы без маркера |
| Классификация в JSON | верно | верно |
| Шапка чанка | точная | нормальная |
| Скорость на M5 | 73–78 ток/с | 23–24 ток/с |

Выдуманный факт в тендерной заявке — худший класс сбоя, поэтому всё, что
выполняется на запрос пользователя, идёт через **Qwen3.5 9B**: плотная 9B,
гибридное внимание (8 из 32 слоёв полные, остальные линейные), KV-кэш на 16k
маленький. Фразы без маркера ловит валидатор вывода (SPEC раздел 7).
Шапки чанков при индексации — тысячи коротких вызовов, где решает скорость,
поэтому там **GigaChat 3.1 Lightning** (MoE 10B, 1.8B активных): эту задачу он
решает точно и втрое быстрее.

`ollama.think: false` обязателен: Qwen3.5 по умолчанию «думает», и скрытые
рассуждения съедают `num_predict` и время.

Это прогон на синтетическом контексте, а не оценка. Решение пересматривается
на 10 контрольных запросах этапа 4; скрипт сравнения переносится в `eval/`.

Окно обеих — не меньше 32k, в конфигурации стоит 16384: так KV-кэш остаётся
умеренным, и бюджет контекста (11000) проходит проверку без изменений. Запас
×1.2 в SPEC заложен под токенизатор GigaChat; для Qwen его нужно перепроверить
на реальных промптах этапа 4.

## Установка

1. **Python-окружение** (нужен Python ≥ 3.13):
   ```bash
   python3 -m venv .venv && source .venv/bin/activate
   pip install -e ".[dev,db,local]"
   ```
2. **Ollama** — приложение с ollama.com. Затем:
   ```bash
   ollama pull qwen3.5:9b
   ollama pull hf.co/ai-sage/GigaChat3.1-10B-A1.8B-GGUF:Q4_K_M
   ```
   Переменные, которые экономят память (задать до запуска Ollama):
   `OLLAMA_MAX_LOADED_MODELS=1`, `OLLAMA_FLASH_ATTENTION=1`,
   `OLLAMA_KV_CACHE_TYPE=q8_0`.
3. **PostgreSQL** — Postgres.app (pgvector в комплекте). Создать базу `bzpo`, затем:
   ```bash
   export BZPO_DB__DSN=postgresql://localhost/bzpo
   python -m bzpo.storage.migrate --dsn "$BZPO_DB__DSN"
   ```
4. **Проверка моделей** (при первом запуске скачает ~3.5 ГБ весов в
   `~/.cache/huggingface`):
   ```bash
   python -m bzpo.providers.local
   ```
   Документ про СЭД должен оказаться выше рецепта и по косинусной близости,
   и по оценке реранкера.
5. Commit эмбеддера уже зафиксирован в `local.embed_model_revision`
   (`1763d603…`, 2026-09-14). При обновлении модели ревизию меняют
   осознанно: она входит в ключ кэша векторов, и после смены корпус
   переиндексируется.

## Что учесть

- **NaN на MPS.** Если самопроверка падает с «вектор не нормализован»,
  переключите `local.dtype: float32`. Это удвоит память эмбеддера.
- **Индексация и LLM в памяти одновременно.** Обогащение (SPEC 4.3) гоняет
  LLM по каждому чанку, а эмбеддер работает параллельно с ним. На 16 ГБ это
  предел, поэтому длинные прогоны лучше запускать без браузера и IDE.
- **Langfuse** в docker-compose съест ещё 2–3 ГБ. На ноутбуке его стоит
  поднимать только на сеансы замеров.
- **Цифры латентности SPEC раздела 11** посчитаны для карты 24 ГБ. На M5
  замерено: Qwen3.5 9B ~23 ток/с, то есть раздел в 1500 токенов пишется
  ~65 с, а 60-секундный бюджет запроса на ноутбуке не выполняется.
  GigaChat Lightning ~75 ток/с. Время реранкинга 50 кандидатов на MPS ещё
  не замерено.
- **`trust_remote_code: true`.** Giga-Embeddings загружается с кодом модели
  из её репозитория на HF. Зафиксированная ревизия заодно защищает от
  подмены этого кода.
