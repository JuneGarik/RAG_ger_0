## 1. Что это за проект одним абзацем

БЗПО — RAG-система (поиск по векторной близости плюс генерация ответа языковой моделью) над корпусом из ~25 проектных документов. Пользователь задаёт вопрос вида «наш опыт внедрения MES на металлургии», система находит релевантные куски документов, факты из БД подтверждений и собирает черновик раздела тендерной заявки со ссылками на источники. Всё крутится on-premise, наружу ходит только сервис эмбеддингов и реранкинга.

Система состоит из двух конвейеров. Офлайн-конвейер один раз прожёвывает документы в поисковый индекс (парсинг, чанкинг, обогащение, векторизация, дедупликация). Онлайн-конвейер на каждый запрос пользователя делает поиск, реранжирование и генерацию. Этап 0.5 — это фундамент под оба, ни один конвейер целиком ещё не собран.

## 3. Что уже написано, по-человечески

**Конфигурация.** Один файл `config.yaml` со всеми ручками системы. Любой параметр перебивается переменной окружения, например `BZPO_SEARCH__TOP_K_FINAL=5`. Секреты (токен сервиса, строка подключения к базе) в файл класть нельзя физически — загрузчик упадёт и назовёт нужную переменную окружения. При старте выполняются кросс-проверки, например что бюджет контекста генерации влезает в окно модели. Невалидная конфигурация означает, что система не стартует, это дешевле молчаливого дефекта.

**Схема БД.** `0001_initial.sql` создаёт 9 таблиц. Справочники проектов и клиентов, реестр загрузок Excel, документы со статусной моделью (pending, parsed, enriched, indexed, failed), разделы и чанки с векторами, артефакты-подтверждения, рёбра графа на будущее. Раннер применяет миграции по номерам, повторный запуск ничего не ломает.

**Модуль изоляции.** Смысл в том, что весь остальной код не знает, где живут эмбеддинги и реранкер. Он зовёт `embedder.embed(texts)` и получает векторы. Внутри спрятаны батчи по 128, усечение длинного входа, 3 повтора с паузами 1/3/9 секунд, учёт Retry-After при коде 429, не больше 4 параллельных запросов и 20 запросов в секунду, нормализация векторов, кэш векторов запросов. Реранкер понимает оба возможных диалекта API (TEI и Cohere-подобный), какой именно у нашего сервиса — узнаем из probe_api. Когда внешний сервис переедет к нам локально, поменяется одна строка конфигурации `external.provider: local`, остальной код не заметит.

**Алгоритмы поиска.** Три чистые функции без базы и сети, поэтому их можно было написать и полностью протестировать уже сейчас. RRF сливает 4 ранжированных списка кандидатов в один, MMR выбирает из топа разнообразные чанки вместо 8 почти одинаковых, boost чуть приподнимает кандидатов из нужной отрасли, из выигранных тендеров и посвежее.

**Тесты.** 99 штук, все обходятся моками (подставными объектами вместо реальных сервисов). Проверяют оба диалекта реранкера, поведение при 429 и таймаутах, битый JSON, перемешанный порядок ответа, ручные расчёты RRF, вырождение MMR без нормировки, порядок таблиц в миграции, границы модулей.

## 4. Что и как запускать

Повседневная проверка, что ничего не сломано. Выполняется из корня проекта, база и сеть не нужны, секунды две.

```bash
python -m pytest tests/ -q
python -m ruff check .
```

Посмотреть итоговую конфигурацию и её хэш.

```bash
python -c "from bzpo.config import load_config; s = load_config(); print(s.config_hash)"
```

Применить миграции — понадобится, когда появится PostgreSQL 16 с расширением pgvector.

```bash
pip install -e ".[db]"
python -m bzpo.storage.migrate --dsn postgresql://user:pass@host/bzpo
```

Разведка внешнего сервиса — когда придут адрес и токен. Скрипт лежит в проекте с этапа 0, отчёт закроет блокирующие вопросы SPEC раздела 15.

```bash
export EMB_URL="https://адрес" EMB_TOKEN="токен"
python about/probe_api.py
```

Запускать пока больше нечего — UI, индексация и поиск по живым данным появятся на этапах 2–4.

## 5. Известные отклонения от SPEC, принятые сознательно

Бюджет контекста. SPEC называет 12000 токенов, но 12000 × 1.2 + 3000 генерации не влезает в окно модели 16384. В конфигурации стоит 11000, тест это охраняет. Решение пересмотреть после пробы GigaChat (задача 0.3) — либо правится SPEC, либо замер покажет, что окно можно поднять.

Латентность при зависшем сервисе. Таймаут чтения 60 с и 3 повтора дают до ~250 с на один неудачный вызов при бюджете 60 с на весь запрос. Параметры ужмутся, когда probe_api покажет реальные скорости сервиса. Сейчас трогать рано.

## 6. Когда переходить дальше

Этап 0.5 по коду закрыт. Из его формального критерия не снят один пункт — миграция 0001 не применялась на настоящей PostgreSQL, потому что базы ещё нет. Это первое действие, как только появится стенд.

Дальше дорога раздваивается. Есть работы, заблокированные внешними событиями, и работы, доступные прямо сейчас.

**Заблокировано, ждём (этап 0 плана, задачи организационные, не кодовые)**

| Ждём | Что разблокирует |

| Адрес и токен внешнего сервиса, прогон probe_api | точные лимиты и диалект в config.yaml, финализация модуля изоляции |
| Карта 24 ГБ и проба GigaChat в Ollama (задачи 0.3, 0.7) | обогащение чанков (этап 2.4 и далее), генерация (этап 4) |

| Сбор 100–150 формулировок от РП (0.4) и якорная разметка (0.5) | эталонный датасет, без него нет метрик этапа 3 |

**Доступно сейчас, без всяких ответов извне (начало этапа 2 и задача 1.1)**

Фиксация JSON-контракта со слоем парсинга документов и 3–4 фикстурных файла (SPEC 4.1, PLAN 1.1). Затем чанкер по этим фикстурам (PLAN 2.3) — самая толстая кодовая задача этапа 2, полностью тестируемая без базы. Затем загрузчик реестра с валидациями на подложенном Excel (PLAN 2.1).

Практическое правило перехода такое. Если pytest зелёный, ruff чистый и в таблице выше появился разблокированный пункт — можно двигаться в него, не дожидаясь остальных. Порядок внутри этапа 2 подсказывает PLAN, колонка зависимостей.

## 7. Гигиена работы с репозиторием

Каждое изменение кода сопровождается прогоном pytest до и после. Новый SQL — только в `storage/`, новый сетевой вызов — только в `providers/`, иначе тест границ уронит CI. Параметры не хардкодятся, а добавляются в `config.py` и `config.yaml`. Решения, отклоняющиеся от SPEC, записываются в README, раздел отклонений, с причиной. Миграции только добавляются новыми номерами, правка применённой миграции запрещена раннером.
